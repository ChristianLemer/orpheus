# CLAUDE.md

Agent instructions for [Claude Code](https://claude.ai/code) when working in this repository.

## Overview

Personal keyboard configuration repository. Not a software project — no build system, no tests. Configurations are used directly by keyboard firmware.

## Structure

```
keyboards/
├── splitkb/          Halcyon Ferris — daily driver (Vial + firmware + SVG)
├── epomaker/         TH40 variants (VIA + QMK)
├── keychron/         Q0, Q4, Q9, Q9 Plus (VIA)
├── vortex/           Core Plus (VIA)
├── windstudio/       Hola Mini (Vial)
├── ymdk/             Ferris (Vial)
└── dz/               DZ60RGB (VIA)
admin/                SVG generation tooling (Nushell)
local/                Nushell keyboard utilities
```

## File Types

- `.vil` — Vial layout (JSON format, primary for split keyboards)
- `.json` — VIA layout
- `.svg` — Keymap visualizations (generated and hand-crafted)
- `.uf2` / `.bin` — Pre-compiled firmware
- `.nu` — Nushell scripts

## SVG Generation

```nushell
nu admin/vil-to-svg.nu keyboards/splitkb/splitkb-halcyon-ferris.vil
```

Uses `keymap-drawer` (via uvx). Custom config in `admin/keymap-drawer.yaml`.

Board geometry lives in `admin/keyboards.nuon`, not in the script — QMK name, LAYOUT
macro or hand-described ortho geometry, row slicing, layer names. Adding a board means
adding an entry there, drawing with `--force`, reading the result, then flipping
`verified` to true. A board that is not verified will not be drawn silently.

The annotated SVG (`-annotated.svg`) is hand-crafted — not generated by any script.

## After Changing a Keymap

```nushell
nu admin/keymap-sync.nu                 # every verified board
nu admin/keymap-sync.nu <path>.vil      # just one
nu admin/keymap-sync.nu <path>.vil --depuis <ref>
```

Redraws the technical SVG and reports what a script cannot fix by itself:

- which keys changed since the last commit
- keys bound to an empty macro — they produce nothing
- that the annotated SVG and the audit are hand-written and now lag behind

**The audit is a living document.** `keyboards/splitkb/splitkb-halcyon-ferris-audit.md`
carries the reasoning behind the layout. When a keymap changes, update its § 1 snapshot,
date any lead that became resolved, and renumber § 7 rather than leaving a hole. An audit
that lies about the current keymap is worse than none — it drifted once already, silently,
for four months.

## The Interactive Page

`docs/index.html` is a standalone page served by GitHub Pages at
`christianlemer.github.io/orpheus/`. Its keymap data is inlined, extracted from
`keyboards/splitkb/splitkb-halcyon-ferris.vil` — so **it goes stale like the annotated SVG
does**. When the Halcyon keymap changes, the page needs regenerating too; nothing does it
automatically.

**Who says what.** Three documents cover this layout, and each owns one job:

| Document | Owns |
|---|---|
| `docs/index.html` | the demonstration — what you can only grasp by operating it |
| `README.md` | the argument — why the layout exists, what it costs, what is in the repo |
| `…-audit.md` | the reasoning — snapshot, weaknesses, open leads, in full |

The page's captions say what to *do*; they must not re-argue the case. When the same idea
appears in two of the three, one of them is wrong — it drifted once already, nine notions
deep, before this rule was written down.

## Commits

Jujutsu (jj) workflow:
- **Format**: `type(scope): emoji description`
- **Types**: `feat`, `fix`, `docs`, `chore`
- **Emojis**: 🎉 initial · ✨ update · 🌐 connectivity · 📄 docs · 🔧 fix
- **Scopes**: keyboard brand or model name (`splitkb`, `halcyon-ferris`, `th40`, `repo`, etc.)

## Working Here

**Modifying a keyboard layout:**
1. Edit the `.vil` or `.json` file (or use Vial at vial.rocks)
2. Regenerate SVG if applicable
3. Commit with keyboard-specific scope

**Adding a new keyboard:**
1. Create directory under `keyboards/<brand>/`
2. Add layout file + firmware if available
3. Update README.md
